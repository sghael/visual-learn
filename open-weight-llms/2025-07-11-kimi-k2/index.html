Kimi K2

How stable training and practiced tool use meet

A model that can describe a spreadsheet operation may still fail to perform it through a tool. Kimi K2 joins two engineering problems: train a large sparse network without numerical instability, and give it experience with actions whose consequences appear in later messages.

4 sections · about 8 minutes · Training

Many stored experts, a few consulted at a time

A mixture-of-experts layer contains several feed-forward networks and a router that chooses which ones process each token. Kimi K2’s model card lists 384 routed experts, eight selected per token, and one shared expert that processes every token. The checkpoint has about one trillion total parameters while activating about 32 billion per token. It inherits multi-head latent attention and the broad sparse-transformer approach from prior work.

[1]

The toy router has eight experts so that every route remains visible. Switch the example and observe which experts light up; then change the number selected. More selected experts means more computation in this layer. The expert labels identify networks, not preassigned professions. The router is learned, and a token’s context influences its representation.

Storing eight books but opening two does not make the shelf smaller. Likewise, unused experts still consume storage. Communication, attention and shared computation also remain. The routed fraction is therefore not a speedup estimate.

An optimizer needs numerical guardrails

An optimizer changes model weights in response to training errors. Muon reshapes matrix-valued weight updates using an approximate orthogonalization, which controls their directional scales. K2 adds QK-Clip because the team observed attention scores growing excessively at scale. After an update, QK-Clip rescales query and key projection weights when observed scores exceed a threshold. The measured scores come from the current batch; the rescaling changes weights used by future batches. It does not alter the forward or backward computation already performed for that batch.

[2]

Here is a scalar illustration of the rescaling. If a query-key product is 400 and a chosen bound is 100, multiply each factor by one half. Their product becomes 100 because 0.5 × 0.5 = 0.25. The actual MLA implementation treats shared and head-specific components differently; this arithmetic only explains why rescaling factors can control a product.

The distinction matters because a training run repeatedly compounds updates. A method that looks useful on a short experiment may become unstable at a much larger scale. The evidence needed is a stable learning trajectory plus downstream evaluation, not merely a lower error at one moment.

A tool trajectory is a lesson with consequences

K2’s launch describes a synthesis pipeline that creates tool specifications, tasks and agents, generates interactions with simulated or real environments, and filters them against task rubrics. The tool definitions tell the learner which inputs an action requires; the returned result supplies evidence for the next action.

[3]

Imagine a toy file-search task. The first call asks for a file that does not exist. A useful training trajectory includes the error, a directory listing, a corrected path, and a final answer grounded in the retrieved content. A dataset containing only successful-looking final answers would omit the recovery behavior.

This is also why simulation quality matters. If a simulated tool always succeeds, the learner receives little practice in handling missing data, ambiguous outputs or rejected arguments. If a judge rewards a confident final answer without checking the result, the pipeline can select a convincing failure. These are consequences of the learning setup, not claims about observed K2 failure rates.

Separate the model from the machinery around it

The July release supplied Base and Instruct checkpoints; the initial Instruct model did not expose the later extended-thinking behavior and did not support vision. Subsequent K2 releases changed those capabilities, so this lesson keeps the initial version separate.

[3]

An application still provides the tool runner, permissions, context handling and error reporting. The model predicts a requested action; surrounding software executes it and returns the result. A benchmark for the resulting agent therefore measures both the checkpoint and its environment. Reproducing a score requires the same tools and evaluation protocol, not just the same model name.

What this tutorial leaves out

  • Muon and mixture-of-experts predate K2; MuonClip and their scaled integration are the release-specific focus.
  • The eight-expert router and scalar clipping arithmetic are teaching models.
