DeepSeek-V4.1-Flash

Share cached history across layers and do less work when reading input

An assistant may read thousands of tokens from a tool before writing a short next action. In that workload, reading and storing input can dominate writing the answer. DeepSeek-V4.1-Flash reorganizes those costs with a causal encoder–decoder, reused attention caches and lower-precision cached values. The release also accepts images natively. [1]

Reading the prompt and writing a reply are different jobs

Prefill processes tokens already present in the input and prepares state for generation. Decode produces new tokens one after another. In an agent loop, a long tool result creates new prefill work even when the next generated instruction is short.

Consider an invented workflow that receives 10,000 input tokens and writes 100 output tokens each round. Reducing work per input token affects many more token-processing events than reducing work per output token. That does not predict total latency: prefill and decode have different parallelism and hardware constraints. It identifies where measurement should begin.

The V4.1 launch describes an asymmetric allocation: 8B active parameters during prefill versus 16B during decode. These are computational participation counts, not the storage size of the 552B-parameter backbone. [1]

Construct decoder memory from the encoder’s output

The model card describes 40 layers divided into a 20-layer causal encoder and 20-layer decoder. Decoder global KV entries are projected from the encoder’s final hidden states, rather than requiring full decoder processing of every old prompt token. Local sliding-window state still requires additional computation. [2]

In a teaching analogy, a research team prepares a structured dossier once, then several readers consult derived views of it. The dossier-building work must preserve what those readers will later need. Here the representations and projections are learned, and the encoder remains causal: it cannot use future positions when processing an earlier one.

This arrangement lets most long-prompt tokens bypass the full decoder path. Generated tokens still traverse the processing needed to produce the next answer. It therefore changes the balance between input and output work instead of making every token uniformly cheaper.

A third compression axis runs through depth

V4 compressed across sequence positions. V4.1’s Compressed Sparse Attention 2, or CSA2, also shares global KV entries across layers. Its Full mode computes cache and selections; Reindex mode shares cache but makes fresh selections; Reuse mode shares both. Every layer retains its own query and local-window state. [3]

Use the widget to inspect a deliberately uniform toy cache. Sixteen layers each storing 4,096 entries of width 128 at eight bits need 8,388,608 bytes. If each group of four layers shares one copy, the modeled global cache falls to 2,097,152 bytes. The calculation assumes exact uniform sharing; actual layer assignments and side channels differ.

Sharing selected indices saves search work. Sharing KV entries saves stored data. They are separate decisions: a layer can reuse the same records yet ask a fresh question about which records matter. That is why the model distinguishes Reindex from Reuse.

Keep persistent memory distinct from working memory

The release distinguishes memory resident in accelerator HBM from persistent cache stored in host memory or on SSD. Its reported improvements compare those separate footprints against V4-Flash. Combining the two into one undifferentiated “memory saved” number would erase an important systems distinction. [1]

CSA2 works with FP4 main KV caching. The model also uses bounded replay: when local-window state is missing, it recomputes a recent segment instead of storing every such state persistently. This reconstruction is approximate, not mathematically identical to replaying all layer dependencies. [3]

An invented bookkeeping example shows the trade. Saving one gigabyte of reusable global state may let a server avoid rereading a long document. Saving additional local state could further reduce recomputation but consume more persistent storage. Recomputing a short recent segment spends arithmetic to save storage and transfer bandwidth. Whether that wins depends on reuse patterns.

Several mechanisms contribute to the release

The model card also documents a vision encoder and projector, Engram conditional memory accessed through token-based lookup, revised residual mixing, and DSpark speculative decoding. These are separate components: image input, sparse memory lookup, stream mixing and generation drafting should not be attributed to cache sharing alone. [2]

The lesson’s cache formula is entries × width × stored layer copies × bits per number. It provides a checklist for understanding what an optimization changes. It deliberately excludes model-weight storage, because a smaller conversation cache does not make hundreds of billions of parameters vanish.

For a workload with many long tool results, input processing and cache persistence can matter enormously. For a short question with a long generated answer, decoding may dominate instead. The same model can occupy different operating regimes, so performance claims need the workload, cache-hit assumptions and numerical precision beside them.

What this tutorial leaves out

  • The cache widget uses invented uniform dimensions and cannot estimate the release’s complete runtime memory.
  • Bounded replay approximately reconstructs local state; it is not exact full-history recomputation.
  • Prefill/decode active counts do not equal total weight-storage requirements.
