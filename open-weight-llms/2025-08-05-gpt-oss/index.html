gpt-oss-20b and gpt-oss-120b

How expert routing, attention, weight precision, and tool handoffs divide the work

A model needs storage for its weights, memory for the conversation, and a way to hand work to tools. These costs come from different parts of the system. gpt-oss makes the distinction visible: experts limit work within a token, attention handles the context, low precision reduces weight storage, and a message protocol connects generation to the host application.

Stored weights and active weights are different

A mixture of experts replaces a single feed-forward network with a bank of networks and a router. The router selects only a few for each token. OpenAI’s release lists 128 experts with four selected in gpt-oss-120b, and 32 with four selected in gpt-oss-20b. The larger model has 36 layers; the smaller has 24. Both are text-only models. [1]

Imagine a workshop with 128 workbenches. A particular job visits four of them. Counting the visited benches estimates part of the work, but all 128 benches still occupy floor space. Likewise, inactive experts save arithmetic for that token without disappearing from memory. Attention and shared operations also contribute to the active parameter count, so four divided by 128 is not the active fraction of the entire model.

The release names round the sizes. The model card gives the following counts; “active” counts parameters used for one token, not how many weights are stored. [5]

A checkpoint is a set of stored tensors. Its file size excludes the additional working memory needed while answering.

Attention can use less history—or less weight

Routing experts does not remove the need to read the conversation. gpt-oss alternates full causal attention with a local window of 128 tokens. Both sizes use 64 query heads sharing eight sets of keys and values. Local windows reduce visible positions in some layers; grouped-query attention reduces the number of key/value sets. Those are separate savings. Full-attention layers still retain a path to earlier context. [5]

There is another, subtler choice. Ordinary attention normalizes its weights to sum to one across the visible tokens. Even an unhelpful set of tokens must receive that whole unit of weight. gpt-oss adds a learned attention sink: an extra score in each head’s normalization, with no corresponding value contribution. The real-token weights can then sum to less than one. The reference implementation includes the sink in the softmax and drops its entry before combining the value vectors. [6]

Try three equally scored tokens with scalar values 2, 6, and 10. Without a sink, their weights are one-third each and the output is 6. Give a fourth, zero-contribution option the same score: every weight becomes one-quarter and the output is 4.5. This is not retrieval of an extra token, and it does not shrink the cache. It changes how much this head contributes to the residual stream.

Store expert weights in fewer bits

The expert weights were released in MXFP4, a microscaled four-bit floating-point format. Groups of low-precision values share scaling information. The model card reports 4.25 bits per expert parameter after this overhead, and says quantization was included during post-training. [5] Inference code must interpret that representation correctly; it is not interchangeable with an arbitrary four-bit integer format. OpenAI provides reference implementations and recommends checking implementations for agreement. [2]

The simplest memory estimate is a useful lower bound. Twenty-one billion weights at sixteen bits require 42 billion bytes. At four bits they require 10.5 billion bytes, if every weight used that format and there were no metadata. Neither assumption describes the complete gpt-oss runtime. Some weights remain at other precisions, and the KV cache, activations, scales, and working buffers require additional memory.

Move between bit widths below. The arithmetic changes exactly; accuracy does not appear on this plot because memory arithmetic cannot predict quantization error. OpenAI’s deployment guide discusses actual supported implementations and their larger memory requirements. [3]

A tool call needs a boundary

A text model can emit the words “I used a calculator” without any calculator running. A working tool system needs an unambiguous handoff: who speaks, which tool receives the request, when the model yields control, and how the result returns. The model generates a request; application code performs the action.

Harmony is the conversation format used by gpt-oss. It distinguishes roles, channels, recipients, and endings. Analysis and final-answer messages occupy different channels. A tool handoff is distinct from ending an ordinary message or finishing the assistant turn. [4] The value of these distinctions is operational: the host knows whether to call a function, resume generation, or return an answer.

For a toy arithmetic task, the host might receive a calculator request, run the calculation, append the result as a tool message, and resume the model. The host must still validate arguments and decide which tools are permitted. A structured request is a format guarantee only to the extent the surrounding system enforces it.

BoundaryWhat the host does next
Message endsMay keep sampling another assistant message.
Tool handoffStops sampling, validates the request, and runs the permitted tool.
Assistant turn finishesStops sampling and delivers the final answer.

These are semantic labels, not literal token spellings. A subtle implementation rule matters: keep the current turn’s analysis while completing its tool round trips; omit earlier completed turns’ analysis when a new user turn begins. Losing the current reasoning context can damage tool behavior. Raw analysis is also not intended as the user-facing answer. [7]

More reasoning changes the inference budget

The released models support low, medium, and high reasoning effort. Their post-training includes supervised learning and reinforcement learning for reasoning and tool use. The model card describes these capabilities and their limits. [5] The levels are instructions the models were trained to respond to. They influence average reasoning length; they are neither exact token budgets nor switches to a larger weight file.

Suppose two settings produce the same final sentence, but one generates many more intermediate tokens and makes two tool calls. They can have very different latency and cost. The relevant budget includes generated tokens, attention over the expanding context, external tool latency, and any retries. Total parameter count hides those differences.

Longer output is not a proof of better reasoning. An intermediate explanation may be mistaken, or fail to describe the computation that produced the answer. Judge the result on a task with a dependable check, compare the same task at each setting, and include unsuccessful attempts in the measurement.

To compare implementations, hold the model, prompt, effort setting, tools, and sampling choices constant. Check both tool-call formatting and task results: a response with valid structure can still be wrong. OpenAI’s compatibility checks and evaluation harnesses address these different failure modes. [2]

What this tutorial leaves out

  • The two sizes share this tutorial because the mechanism is shared; their parameter and expert counts differ.
  • The four-bit chart is an ideal lower bound, not a claim that the whole model uses four bits or fits in a particular device.
  • This tutorial does not infer an undisclosed full training-data recipe from the released weights.
  • The attention sink changes normalized value mixing; it is not an extra cached token, a context compressor, or a guarantee of faithful reasoning.
  • Reported checkpoint sizes, ideal packed-weight bytes, and peak serving memory describe different quantities.
