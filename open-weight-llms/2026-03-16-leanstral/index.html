Leanstral / 1.5

Turn a proposed proof into a checked artifact

A language model can write a convincing mathematical argument containing a hidden mistake. A proof assistant changes the feedback available: it checks a formal proof against an exact statement and explicit assumptions. Leanstral brings that feedback into a downloadable model trained for proof engineering inside real repositories. [1]

Begin with something a checker can mean

Consider the statement “adding zero preserves a number.” Before checking it, specify the objects and operation: natural numbers with ordinary addition. A proof must establish the property for every allowed number, not merely test zero, one and a million.

Now change the requirement to “incrementing always increases a number.” It holds for unbounded natural numbers, but can fail for fixed-width arithmetic that wraps at its maximum value. The English wording was almost unchanged; the mathematical objects changed the answer. A proof assistant checks the formal claim it receives. Choosing a claim that matches the intended program remains a separate job.

Lean’s kernel checks proof terms against their types and permitted assumptions. Automated tactics can help construct the proof, but a persuasive explanation alone is not that proof. This division permits a fallible generator to propose candidates for a more tightly specified checker. [2]

Learn to work inside the feedback loop

Leanstral’s March release targets Lean 4 repository work through Mistral Vibe, including the Lean language-server tool interface. Its Apache 2.0 checkpoint has 119B total parameters and about 6.5B active parameters. Sparse mixture-of-experts architecture is inherited machinery; the distinctive emphasis here is formal code-agent work. [3]

Imagine the agent needs an auxiliary lemma before the requested theorem can compile. It searches the library, writes a candidate, inspects the remaining proof goal, and revises the missing step. The intermediate error is useful information about what remains to establish.

A final check also has to preserve the requested statement. Quietly weakening the theorem would make an easy proof of the wrong task. Leanstral’s evaluation uses repository-level proof engineering rather than only isolated competition questions. [1]

Reward a completed trajectory

The July Leanstral 1.5 update [6] and report describe domain mid-training, supervised agent trajectories, and reinforcement learning with CISPO. Training environments include repeated theorem attempts with compiler feedback and longer repository tasks with file access and Lean tools. Final checks include statement preservation and allowed-axiom restrictions. [4]

Think of a trajectory as an entire workshop session: inspect files, try a lemma, receive a diagnostic, repair a proof, and submit. Reinforcement learning can associate the eventual checked result with model-generated choices along that session. It need not pretend that every fluent intermediate sentence deserves a reward.

Long sessions also need memory management. The 1.5 system compacts context while preserving the original instruction. Its ordinary Vibe evaluation does not require a specialized proof-search scaffold beyond compaction. A long total trajectory therefore does not imply that every earlier token remains in the model’s context simultaneously. [4]

More attempts create more opportunities

A verifier can recognize a valid candidate among several attempts. Suppose, purely for illustration, each independent attempt succeeds with probability 0.2. Four attempts then succeed at least once with probability 1 − 0.8⁴ ≈ 0.5904. Real attempts may share the same blind spot, so independence is an assumption, not a model property.

The scheduling widget isolates another distinction. Four independent jobs taking 3, 2, 4 and 1 time units require ten units on one worker. More workers can reduce elapsed time, but the total work remains ten units. Actual model serving adds batching effects, memory limits and tool overhead.

Leanstral reports results with multiple attempts per problem. The widget represents independent trials, not communicating proof agents or a measured Leanstral speedup. Coordinated multi-agent proof decomposition is future work in the report. [4]

A passed check has a precise boundary

A Lean file can contain an unfinished-proof placeholder, or depend on an extra axiom. Compilation alone is therefore too weak a success criterion. Lean provides mechanisms to inspect a theorem’s assumptions, and the task must say which are allowed. [5]

Ask three separate questions of a verified result: did the proof check, were its assumptions permitted, and does its formal statement express the intended requirement? Leanstral’s contribution is a trainable, inspectable agent around this workflow. Human-readable confidence should never substitute for the actual checked artifact.

What this tutorial leaves out

  • March 2603 checkpoint facts and July 1.5 training details are labeled separately.
  • A checked proof establishes its formal statement under its assumptions; it does not automatically validate the English specification.
  • The parallel widget models independent scheduling only, not actual serving performance or coordinated agents.
