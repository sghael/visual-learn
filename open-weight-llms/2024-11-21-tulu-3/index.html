Tülu 3

How a checkable answer becomes a training signal

A preference judge can reward a persuasive answer that is wrong. Some tasks offer a sharper signal: run a test, compare a numerical answer, or check a formatting constraint. Tülu 3 made verifiable rewards part of a documented post-training recipe, with released data and code that others could examine.

Different stages teach different behavior

A pretrained model learns to predict text. Supervised fine-tuning shows it examples of the responses an assistant should produce. Preference optimization then changes its relative preference for chosen and rejected responses. Reinforcement learning can generate new answers and reward their outcomes.

Tülu 3 combines curated supervised data, preference tuning with DPO, and reinforcement learning with verifiable rewards, or RLVR. The initial release built on Llama 3.1 models. The contribution includes a transparent, tested recipe rather than a claim to have invented every ingredient. [1]

Think of teaching arithmetic. Worked solutions demonstrate a method. Comparing two explanations teaches style and preference. Checking a newly attempted problem gives feedback on an outcome the student generated. The signals overlap, but they are not interchangeable.

A reward is only as good as its checker

For the question “What is 3 × 2?”, a toy verifier might extract the final number and compare it with six. That is easy to audit. It also ignores most of the answer. An explanation containing incorrect intermediate arithmetic can still end in six and receive reward.

Try the “Flawed reasoning” example below. Then switch to exact-string checking and try the formatted answer. The first checker is too permissive about reasoning; the second is too strict about formatting. Both are deterministic. Deterministic does not mean that the check measures everything a reader cares about.

In the actual recipe, verified outcomes replace learned reward-model scores for selected tasks. Tülu 3 uses PPO in this stage, including controls such as a penalty for drifting from a reference policy. It does not use the group-normalization toy associated with GRPO in the DeepSeek-R1 lesson. [2]

Why reward can change future attempts

A language model assigns probabilities to tokens, and therefore to complete responses. In reinforcement learning, the model samples a response, receives a score, and adjusts its parameters so useful responses become more likely under the training objective. The update is mediated by the probability of the sampled tokens; the verifier need not be differentiable.

Suppose a policy produces a successful solution one time in ten. Successful samples provide evidence for shifting its distribution. If every attempt fails, a sparse binary reward gives little information about which wrong step to repair. If every attempt succeeds, the task may no longer teach the desired distinction. Task difficulty and prompt selection therefore matter alongside the optimization algorithm.

This example explains the mechanism without claiming a universal learning curve. A finite sample can be lucky, a verifier can be exploited, and increasing training reward can fail to improve a held-out test. A useful experiment separates the tasks used for learning from those used to measure generalization.

An open recipe makes the comparison inspectable

The Tülu project publishes post-training data and a codebase covering supervised fine-tuning, DPO, and RLVR. [3] The practical scientific benefit is the ability to vary a component while keeping others fixed. For example, keep the same base model and supervised checkpoint, then compare two reward definitions on an untouched evaluation set.

That experiment answers a narrower and more useful question than comparing two unrelated chatbots. A difference between unrelated systems might arise from architecture, pretraining data, prompt templates, sampling, or evaluation contamination. A controlled recipe lets researchers isolate part of the explanation.

The model-weight license remains tied to the underlying Llama release; open training code does not replace it. The initial model card identifies the base model and release artifacts. [4] Treat openness as several separately inspectable properties: weights, data, code, checkpoints, and evaluation procedures.

What this tutorial leaves out

  • The checker is a pedagogical example, not a copy of the released verifier.
  • RLVR is a source of rewards, not a synonym for one optimizer: Tülu 3 uses PPO.
  • This lesson covers the original 8B/70B recipe; the later 405B extension is not the November release.
