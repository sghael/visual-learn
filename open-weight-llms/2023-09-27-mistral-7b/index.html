Mistral 7B

Share the memory; move the window

A language model can be small enough to fit in memory and still become expensive when a conversation grows. Mistral 7B makes that distinction visible: its weights stay fixed, while the working memory used to remember previous tokens can grow. Its original release combined two existing attention ideas in a compact, downloadable model. [1]

Why yesterday’s tokens cost memory

Imagine completing the sentence “Maya put the red notebook beside the blue notebook; she picked up the red …” To predict the next token, an attention layer compares a new query with stored keys and blends their associated values. A key helps decide where to look; a value supplies information from that location.

The stored keys and values form the KV cache. Caching avoids rebuilding the entire past for every generated token. The trade is storage: another token means another set of entries, repeated at many layers. Model weights are the learned machinery; the cache is temporary state for this particular conversation. Two simultaneous conversations share weights but need separate caches.

This distinction suggests two independent questions: how many versions of each token must we store, and how far back must each attention operation look? Mistral addresses both. Neither change implies that a model has perfect recall.

Many questions can share the same records

In ordinary multi-head attention, separate attention heads have separate key and value representations. Grouped-query attention, or GQA, keeps multiple query heads but lets a group share keys and values. The GQA paper places this design between fully separate heads and multi-query attention, which shares one KV set across every query head. [2]

A teaching example makes the arithmetic concrete. Suppose 32 query heads share eight KV heads: four query heads consult each stored representation. They may still ask different questions because their queries differ. Sharing the filing cabinet does not require every reader to ask for the same file.

Move the context slider. Doubling the number of stored tokens doubles this cache estimate. Switching from 32 KV heads to eight quarters it at the same length and precision. The widget uses Mistral v0.1 dimensions, but deliberately excludes its rolling-window eviction: it isolates head sharing. [3]

A local window changes the pattern of work

Mistral v0.1 uses a 4,096-token sliding attention window. Each layer reads a recent neighborhood instead of every prior position. A rolling cache can reuse old storage slots as tokens leave that neighborhood. These are the original model’s settings, not a promise that every later Mistral checkpoint uses the same attention pattern. [3]

The small diagram uses 16 positions and a four-position window. Choose a query near the end, then compare full and local attention. Full attention keeps adding visible predecessors. Local attention moves a fixed-size group across the sequence. The missing cells represent work that this layer does not perform.

Local access does not mean earlier information vanishes immediately from the whole network. A recent token’s representation may already contain information gathered at a previous layer. Picture a relay: one person carries a message to the next. Repeated short hops permit a longer path, although details may be lost along it.

Savings multiply, while quality still needs testing

Consider an invented workload with 32,768 retained positions before any eviction. A window of 4,096 would reduce retained positions eightfold. Eight KV heads instead of 32 reduce head storage fourfold. In this ideal cache arithmetic, applying both gives 8 × 4 = 32 times fewer stored elements than full-history, fully separate KV heads. This is a calculation about the cache, not a measured speedup or total GPU-memory reduction.

The two controls remove different redundancy: GQA shares representations across heads; the window bounds access across time. Sparse attention patterns predate Mistral, as the Sparse Transformer work illustrates. Mistral’s contribution here is a practical combination, rather than the invention of locality. [4]

A useful evaluation must ask whether the model can retrieve the particular information a task needs. A theoretical path through many layers is weaker evidence than a correct answer about a distant detail. The original paper’s benchmark results describe its evaluation setup; they do not turn the cache calculation into a guarantee of accuracy.

What became easier to build

The September release made both base and instruction-tuned weights available under Apache 2.0. That gave developers a model they could inspect, adapt and host, with the release’s licensing conditions. The attention changes helped make serving a smaller model an architectural subject rather than merely a question of buying more memory. [1]

When comparing a new model, carry three separate numbers forward: weight storage, per-conversation cache storage, and work per generated token. A change can improve one while leaving another almost untouched. Those distinctions become even more important in Mixtral and DeepSeek, where parameter sparsity and cache compression take different paths.

What this tutorial leaves out

  • All widgets are teaching calculations, not benchmarks.
  • The GQA widget intentionally omits v0.1 sliding-window eviction so head sharing can be inspected independently.
  • Reachability through stacked local layers does not guarantee long-range retrieval quality.
