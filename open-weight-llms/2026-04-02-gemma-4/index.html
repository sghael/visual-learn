Gemma 4 · E2B, E4B, 26B-A4B, 31B, later 12B

How a family separates weight memory, token computation and sensory encoding

A model name with a “B” suffix no longer tells the whole resource story. Some parameters execute selectively, some embeddings can be managed separately, and some models add large sensory encoders. Gemma 4 is a useful exercise in reading those distinctions before comparing models.

One family contains different architectures

Google released the first Gemma 4 weights on April 2, 2026 under Apache 2.0. The initial family included E2B, E4B, a 26B mixture-of-experts model and a 31B dense model. The encoder-free 12B model was a separate June 3 addition. Keeping those dates separate avoids projecting the later architecture back onto the initial release. [1] [2]

The technical report calls the MoE model 26B-A4B and gives about 3.8B active parameters. E2B and E4B use per-layer embeddings inherited from Gemma 3n; their effective 2.3B/4.5B accounting differs from their roughly 5B/8B total parameters. “Effective,” “active,” and “total” describe different counting conventions. [3]

Imagine two inventories. The first lists every stored number. The second lists numbers involved in one token’s computation. Sparse routing changes the second without deleting the first. An embedding table that is stored or accessed differently requires yet another explanation. Compare like with like before drawing a memory or speed conclusion.

The 12B addition removes separate sensory encoders

In a conventional encoder-based design, an image network transforms pixels before a language model sees their vectors. Gemma 4 12B instead uses lightweight projections of image patches and raw audio chunks into the language model’s embedding space. The June release describes this as a unified, encoder-free architecture. [2]

Encoder-free does not mean preprocessing-free. Inputs still need a numerical shape compatible with the transformer. The report describes 48-by-48 RGB image patches and 40-millisecond audio chunks. A projection changes the dimension of each input vector; positional information preserves where an image patch came from. [3]

Think of a small picture divided into a grid. Flatten one patch’s red, green and blue values into a list of numbers, then multiply by a learned matrix to obtain a token vector. Repeat for other patches. This invented grid explains the operation without implying that a raw patch is already a recognized object.

Moving work does not make it disappear

The direct projection is smaller than a separate deep vision encoder, but the transformer must now learn to build useful sensory representations. A model may save one component while increasing demands elsewhere in training or inference. “Unified” identifies where the work happens, not a proof that every task becomes cheaper.

Consider reading a handwritten total on a receipt. The model needs to distinguish ink marks, identify digits, connect the total to a label, and answer the question. An encoder-based system performs part of that transformation before the language backbone; an encoder-free system learns more of it in the backbone.

This comparison is architectural. The toy flow contains no measured accuracy or runtime, so it cannot determine the best design for a particular camera feed, document collection or device.

Train while seeing the rounding error

On June 5, Google released Gemma 4 checkpoints prepared with quantization-aware training, including Q4_0 and mobile-oriented formats. QAT simulates low-precision effects during training so that weights can adapt to the distortion that deployment will introduce. It is an application of an established compression method. [4]

For an invented weight of 0.37, a coarse allowed grid might force storage as 0.4. Applying that rounding only after training surprises the model. Exposing the rounding during training lets surrounding weights adjust. It cannot preserve an arbitrary real-valued network perfectly, but it changes the optimization problem in a useful way.

The 4-, 8- and 16-bit buttons show only ideal storage for twelve billion weights: 24 GB at sixteen bits, 12 GB at eight, 6 GB at four. Actual Gemma checkpoints include format overhead and mixed-precision components. The figure deliberately avoids a claim that a specific device can run the complete model.

A small drafter can propose several next tokens

The July technical report also documents a multi-token-prediction drafter for speculative decoding. It describes a small autoregressive head that uses the main model’s representations and cached attention information. Drafts are proposals to be checked, not permission to bypass the main model’s distribution. [3]

An illustrative writer proposes “the answer is six” in one draft. If the verifier accepts the first three tokens but rejects “six”, the accepted prefix can be retained and the disagreement handled by the decoding algorithm. The opportunity is to amortize expensive main-model work over several accepted tokens.

The gain depends on acceptance rate, draft overhead and hardware. Gemma 4 therefore demonstrates several independent routes to efficiency: selective computation, different sensory interfaces, fewer stored bits, and cheaper proposals for generation. A responsible comparison identifies which route changed and measures its effect under the same workload.

What this tutorial leaves out

  • The April folder date is the family launch; 12B and QAT additions are explicitly dated June.
  • Effective, active and total parameter counts are not interchangeable.
  • The precision figure is an ideal calculation and makes no device-fit claim.
  • Encoder-free applies to the 12B addition, not every Gemma 4 variant.
