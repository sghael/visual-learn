Models and model sizes

K2 Horizon contains six decoder-only transformers. They share the same general architecture, training method, interfaces, and deployment tooling. The 0.9B model uses a smaller tokenizer. The 36B and 375B models also replace dense feed-forward layers with sparse Mixture-of-Experts layers.

Intended deployment

IFM describes the 0.9B model as a wearable model, the 3.7B and 7B models as on-device models, the 32B and 36B-A4B models as local-server models, and the 375B-A23B model as a datacenter model. These are vendor positioning statements. Real deployment requirements depend on weight precision, KV-cache size, serving software, memory bandwidth, and latency targets.

The 0.9B model has a 64,256-token vocabulary; the other models use 250,624 tokens. A smaller embedding table leaves more of a small model's parameter budget for transformer layers. The 0.9B model advertises a 131,072-token context using YaRN scaling. The other five configurations advertise 524,288 tokens after long-context midtraining.

Transformer layers

Every K2 Horizon model is a decoder-only transformer. A token's hidden vector passes through a stack of identical layers, and each layer has two halves: an attention block that mixes information across positions, and a feed-forward block that transforms each position on its own.

The fleet uses three variants of this layer. Switch between them below and press Route a token to watch where a single token's computation goes.

How MoE reduces per-token compute

A dense transformer executes each layer's attention and feed-forward weights for every token. A Mixture-of-Experts (MoE) layer replaces one feed-forward network with a pool of smaller experts and a router that selects a subset per token. The 375B model has 192 routed experts plus one shared expert in each layer and selects 8 routed experts per token. IFM summarizes the result as 375B total parameters and about 23B active parameters per token. Active parameters are a model-size convention, not a direct measure of FLOPs or latency.

All experts still occupy memory, even though each token uses only a subset. The 36B-A4B model therefore needs storage and accelerator memory closer to a 36B model while executing about 4B parameters per token. It will not necessarily match the latency of a dense 4B model: expert routing, memory traffic, batching, and the serving implementation also matter.

MoVA routes value projections

Mixture-of-Value Attention (MoVA) adds sparse routing to the attention block. Attention computes query, key, and value projections. Query-key scores determine how much weight each earlier position receives. Value projections supply the vectors combined by those weights.

In MoVA, the single value projection is replaced with a pool of value experts. A router picks a small subset for each token, and only those value projections are computed. In the 36B-A4B model each layer holds 64 value experts and activates 4 per token, alongside its 100 feed-forward experts of which 8 are active.

Simplified diagram. The left side shows query-key attention scores. The right side replaces one value projection with a routed pool. Increasing the pool adds stored parameters; increasing the active count adds per-token computation.

Routing value projections increases the number of learned value transformations without computing all of them for every token. IFM has published the configuration but has not yet documented the routing function in enough detail to reproduce it. The diagram therefore shows the configured pool and active-expert counts. Its token routing is random and illustrative.

The 375B-A23B config sets mova_num_experts: 0. Among the six released models, only the 36B-A4B configuration uses MoVA.

Uno decodes multiple tokens per pass

Autoregressive decoding commits one token at a time. The 7B and 0.9B models have optional Uno adapters based on IFM's paper Unlocking Lossless Speedups in LLMs via Discrete Diffusion. Uno proposes several tokens together, then verifies them against the base model's distribution.

Uno adds a second set of lightweight weights (LoRA adapters, rank 128) trained with a discrete-diffusion objective. Those weights can fill in a whole block of masked positions in parallel. A sampler the paper calls Ψ-Spec then checks the drafted block against the original autoregressive model and keeps the longest prefix the base model agrees with. Because acceptance is decided by the base model's own distribution, the output is provably the same distribution as ordinary decoding.

Uno uses lightweight diffusion weights instead of a separate draft model. In IFM's experiments, it used fewer added parameters and less inference memory than the compared speculative-decoding methods. Ψ-Spec samples from the base autoregressive distribution, so the acceleration does not change that target distribution. The published 7B-Uno results report 70.1% on SWE-bench Verified, 77.1% on GPQA Diamond, and 98.9% on MATH500.

Two samplers ship in the Uno repository: a linear sampler that maximises system throughput at large batch sizes and a tree sampler that minimises per-request latency.

375B training stages

IFM documents the 375B-A23B training stages and has published many intermediate checkpoints. Select a stage for details. The line above the track shows the configured context growing from 8K to 512K tokens during midtraining.

Specialized RL models and merging

IFM trained five RL variants for knowledge work, instruction following, search, tool use, and reasoning, then merged them into the released model. Supervised fine-tuning ran in three phases totaling roughly 330 billion tokens.

Reasoning traces, tool calls, and agent trajectories enter during midtraining. The model card describes the 512K context as native from those stages onward.

Training data

IFM describes a roughly 20-trillion-token corpus, about half synthetic. Nearly 17% consists of problem-solving trajectories with explicit reasoning steps. The public Hugging Face organization links pretraining and midtraining datasets; availability and documentation are still changing during the rollout.

Proportions are as stated in IFM's release materials; the exact split between synthetic reasoning data and other synthetic data is not broken out, so the inner ring shows it as one region.

The published data includes tool definitions in JSON, XML, and Markdown. This teaches the models several common tool schemas; it does not guarantee that every deployed model will follow every schema reliably. The 375B model card recommends reasoning_effort="high", temperature 1.0, and top-p 0.95.

Reported benchmark results

The chart reproduces comparisons selected and run by IFM for each model card. Use it to inspect the reported scores, not as an independent ranking. Different model cards use different competitors and sometimes different evaluation harnesses.

Scores are percentages except GDPVal-AA, which is an Elo rating. Numbers are transcribed from the Hugging Face model cards as of September 2026 and are self-reported by IFM.

In IFM's chosen comparisons, the 0.9B, 3.7B, and 7B models lead several math and software-engineering results. The 36B-A4B model scores well on the listed terminal and tool-use tasks but trails its comparison model on GPQA Diamond. The 32B results are provisional because they use a Stage 1 checkpoint. For the 375B model, the chart shows IFM's comparisons with open-weight and closed models; these are self-reported results rather than a controlled third-party evaluation.

IFM reports 70.2% raw accuracy on Terminal-Bench 2.1. Its later reward-hacking audit removed flagged trials and produced an adjusted score of 66.9%. The chart uses 66.9% and labels it as the audited correction.

Getting the models

All six model repositories are under the IFM organization on Hugging Face. The model cards provide vLLM and SGLang serving recipes. IFM lists Compass, Cerebras, AWS, and Nebius as hosted API partners. Uno adapters and code are in github.com/ifm-ai/uno.
