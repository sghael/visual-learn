K2 Horizon, explained visually

Chapter 1

One family, six sizes

K2 Horizon is not one model but a fleet built on a single core architecture. All six share a tokenizer, a training recipe, and the same deployment tooling. What changes across the fleet is scale, and, for the two largest, how parameters are spent.

The chart below places each model on a logarithmic scale. Bars show total stored parameters. The darker inner bar shows the parameters that actually run for each token. For dense models the two are equal. For the sparse models, most parameters sit idle on any given token.

Where each size is meant to run

IFM pitches the fleet by deployment target rather than by benchmark alone. The 0.9B model is sized for wearables such as watches and glasses. The 3.7B and 7B models target phones and other on-device use. The dense 32B and sparse 36B-A4B models are the local-hosting and on-premise tier. The 375B-A23B flagship is for enterprise reasoning workloads behind an API.

Two details in the spec sheet are worth noticing. The 0.9B model uses a much smaller vocabulary (64K instead of 251K) because in a model that small the embedding table would otherwise dominate the parameter budget. And its context is 128K rather than 512K, reached through YaRN scaling of rotary position embeddings rather than the native long-context midtraining the larger models get.

Chapter 2

Inside one layer

Every K2 Horizon model is a decoder-only transformer. A token's hidden vector passes through a stack of identical layers, and each layer has two halves: an attention block that mixes information across positions, and a feed-forward block that transforms each position on its own.

The fleet uses three variants of this layer. Switch between them below and press Route a token to watch where a single token's computation goes.

Why sparsity

A dense model spends every parameter on every token. A Mixture-of-Experts (MoE) model replaces the single feed-forward network with a pool of smaller "experts" and a tiny router that picks a few of them per token. The 375B flagship has 192 routed experts plus one shared expert in each layer and activates 8 routed ones per token. That is how 375 billion stored parameters become only 23 billion of compute per token.

The catch is memory. Every expert must be loaded even though most sit idle, so an MoE model needs the memory of its total size but runs at the speed of its active size. That trade is what makes the 36B-A4B model interesting for local hosting: it needs roughly the RAM of a 36B model but generates tokens about as fast as a 4B one.

Chapter 3

Mixture-of-Value Attention

MoE sparsity has traditionally lived only in the feed-forward half of the layer. K2 Horizon's MoVA brings the same idea into attention itself. Attention computes three projections of each token: a query, a key, and a value. Queries and keys decide where to look. Values are what gets carried back.

In MoVA, the single value projection is replaced with a pool of value experts. A router picks a small subset for each token, and only those value projections are computed. In the 36B-A4B model each layer holds 64 value experts and activates 4 per token, alongside its 100 feed-forward experts of which 8 are active.

Left: the standard query/key path is unchanged, so MoVA stays compatible with FlashAttention, grouped-query attention, and sparse attention. Right: the value path routes through a pool. Capacity grows with the pool size; per-token compute grows only with the number of active experts.

Why put sparsity here? Attention is the mechanism that assembles information from across the context. Adding capacity to the values gives the model more ways to express what to retrieve from each attended position, without changing the cost of deciding where to attend. IFM's public materials describe MoVA at this level and promise the training code; the exact routing function is not yet documented, so the diagram shows the structure rather than a specific routing rule.

The 375B-A23B flagship ships with mova_num_experts: 0 in its config. MoVA is currently used only in the 36B-A4B model, which is why that model carries "MoVA" in its name.
Chapter 4

Uno: drafting many tokens at once

A standard language model generates one token per forward pass. The 7B and 0.9B models ship with an optional Uno adapter, from IFM's paper Unlocking Lossless Speedups in LLMs via Discrete Diffusion, that lets them emit several tokens per pass without changing what they would have said.

Uno adds a second set of lightweight weights (LoRA adapters, rank 128) trained with a discrete-diffusion objective. Those weights can fill in a whole block of masked positions in parallel. A sampler the paper calls Ψ-Spec then checks the drafted block against the original autoregressive model and keeps the longest prefix the base model agrees with. Because acceptance is decided by the base model's own distribution, the output is provably the same distribution as ordinary decoding.

Compared with speculative decoding, there is no separate draft model to load, and the adapter adds the fewest parameters and the lowest inference memory of the methods the paper compares against. Compared with diffusion language models, quality is unchanged because the base model still has the final say. The 7B-Uno release keeps the base model's scores: 70.1% on SWE-bench Verified, 77.1% on GPQA Diamond, 98.9% on MATH500.

Two samplers ship in the Uno repository: a linear sampler that maximises system throughput at large batch sizes and a tree sampler that minimises per-request latency.
Chapter 5

How the flagship was trained

IFM publishes the stage-by-stage recipe, and will release intermediate checkpoints so capability changes can be studied across training rather than only at the end. The track below follows the 375B-A23B model. Pick a stage for details. The line above the track shows how the context window grows from 8K tokens to 512K during midtraining.

Reinforcement learning by specialists, then merging

Rather than one RL run over everything, IFM trained five separate expert models with reinforcement learning, one each for knowledge work, instruction following, search, tool use, and reasoning, then merged them into a single model. Supervised fine-tuning ran in three phases totalling roughly 330 billion tokens, with the first phase for domain coverage and later phases for quality.

A distinctive choice: post-training-style data (reasoning traces, tool calls, agent trajectories) was mixed into midtraining rather than held back for the end. The 512K context is native from the midtraining stages onward.
Chapter 6

What ~20 trillion tokens are made of

Each model was trained on roughly 20 trillion tokens. About half of that is synthetic, generated for the purpose, and nearly 17% of the total consists of problem-solving trajectories with explicit reasoning steps. The pretraining corpus itself is part of the release.

Proportions are as stated in IFM's release materials; the exact split between synthetic reasoning data and other synthetic data is not broken out, so the inner ring shows it as one region.

One agent-oriented detail: tool definitions appear in the training data in three formats, JSON, XML and Markdown, so the deployed models accept any of them. The 375B model card recommends reasoning_effort="high" with temperature 1.0 and top-p 0.95 for its intended workloads.

Chapter 7

How each size compares at its scale

IFM's claim is "best open model at every size", not "best model". The chart lets you check that claim size by size against the competitors IFM chose in each model card. Pick a model, then hover the bars.

Scores are percentages except GDPVal-AA, which is an Elo rating. Numbers are transcribed from the Hugging Face model cards as of September 2026 and are self-reported by IFM.

The pattern that emerges: the three small models lead their brackets outright, especially on mathematics and software engineering, where a 3.7B model reaching 68.6% on SWE-bench Verified is unusual. The sparse 36B-A4B is strongest on agentic tasks (terminal use, tool calling) and trails on graduate-level science questions. The dense 32B is the weak spot of the fleet: it trails Qwen3.8-27B on every benchmark in its own model card, sometimes by a wide margin. The 375B flagship sits close behind the best closed model in most categories while matching or beating open-weight models up to 2.6 times its size.

After an internal audit found reward hacking in one evaluation, IFM corrected the 375B model's Terminal-Bench 2.1 score from 70.2% to 66.9%. The chart shows the corrected figure. Corrections like this are one argument for the "fully open" approach in the next chapter.
Chapter 8

Open weights versus fully open

Most "open" models release weights and a license. K2 Horizon's founder, Eric Xing, frames the release differently: science works when others can see the data, follow the method, reproduce the result, and improve on it. The table shows what that means concretely, and what each item lets you do.

Getting the models

All six are on Hugging Face under the IFM organisation, with day-one support in vLLM and SGLang and hosted API access through Compass, Cerebras, AWS and Nebius. The Uno adapters live in a separate repository at github.com/ifm-ai/uno.
