How JAX runs your code, next to how PyTorch does

JAX and PyTorch both let you write array math in Python and run it on accelerators. They get there by opposite routes: PyTorch executes each operation the moment you call it, while JAX traces your whole function once and hands the record to a compiler. Almost every difference between the two frameworks, and between the chips they favor, follows from that one choice.

Two philosophies, one goal

Under a few lines of Python sits a tower of software. The two towers look alike from a distance, but each layer answers the question when do we decide what to run? differently.

PyTorch answers “now.” Calling torch.matmul sends one operation through a dispatcher to a pre-built CUDA kernel, which starts executing on the GPU while Python moves on to the next line. The program is the Python program.

JAX answers “later.” Calling a function wrapped in jax.jit first records what the function does to abstract, shape-only stand-ins for its inputs. That record, a jaxpr, is lowered to StableHLO and handed to XLA, which compiles the whole function into one optimized executable. The program is the trace.

Hover any layer to read what it does. Note the crossings: JAX runs on NVIDIA GPUs through XLA:GPU, and PyTorch reaches TPUs through PyTorch/XLA. Each framework's home turf is simply where its design shines.

Tracing: jit runs your Python once

jax.jit does not read your source code. It calls your function with tracers, objects that know their shape and dtype but hold no values, and records every JAX operation they flow through. The record is a jaxpr: a tiny functional language with one equation per primitive.

Three consequences follow, and they explain most first-week surprises:

  • Python runs at trace time, not run time. A print inside a jitted function prints once, shows a tracer, and stays silent on later calls with the same shapes.
  • Value-dependent control flow cannot be recorded. if x.sum() > 0: needs a concrete boolean; a tracer cannot provide one. jnp.where or lax.cond record both branches instead.
  • Shapes are part of the signature. A new input shape triggers a new trace and compile. A shape JAX has seen runs the cached executable immediately.

Eager PyTorch has none of these rules because there is no trace: your Python runs on every call, if sees real values, and shapes vary freely. torch.compile reintroduces a similar contract. TorchDynamo captures a graph with guards on shapes and types, then falls back to eager at a “graph break.”

Fusion: why a compiled program moves less memory

Modern accelerators are starved, not slow. An H100 can perform roughly a thousand trillion bf16 floating-point operations per second but read only about 3 terabytes per second from its memory. Elementwise operations like relu or add do one flop per byte and spend nearly all their time waiting on memory.

In eager PyTorch every operation is its own kernel: it reads inputs from high-bandwidth memory (HBM), computes, and writes the result back. A chain of five small ops means five round trips. XLA, and likewise the Inductor backend of torch.compile, fuses neighbouring elementwise ops into a single kernel, so intermediate values live in registers and never touch HBM. Reductions such as softmax and library calls such as matmul are natural fusion boundaries, though a compiler can often bolt a pointwise “epilogue” onto a matmul.

Autodiff: a transformation, not a tape

Both frameworks do reverse-mode automatic differentiation, and both produce the same numbers. They differ in what a gradient is.

In PyTorch, gradients are a side effect of running forward. Each tensor operation appends a node to a dynamic graph, the “tape.” loss.backward() walks it in reverse and accumulates results into each parameter's .grad. The tape is rebuilt every iteration, so any Python control flow simply works.

In JAX, jax.grad(f) is a new function. JAX traces f, applies the chain rule to its jaxpr (a forward-mode jvp, then a transposition to get reverse mode), and returns a function you can call, jit, vmap, or differentiate again. Nothing is stored on your arrays and nothing accumulates: the gradient is a return value.

Composable transformations

Because grad returns a plain function, it composes with the rest of JAX's transformations. jit compiles, grad differentiates, vmap vectorizes. Each takes a function and returns a function, so they stack in any order.

vmap deserves a closer look. You write the code for one example; vmap rewrites every primitive to carry an extra batch axis, so a dot becomes a batched dot_general and a scalar loss becomes a vector of losses. Per-example gradients, a notorious chore in eager frameworks, are just vmap(grad(loss)).

PyTorch has grown the same ideas under torch.func (formerly functorch), with torch.func.grad and torch.func.vmap, plus torch.compile for compilation. They sit beside the eager, object-oriented core rather than beneath it.

State, randomness and the pure-function contract

A traced function is only reusable if it behaves the same every time it sees the same inputs. So JAX asks for pure functions: parameters, optimizer state and random keys are passed in and returned as explicit values, and arrays are immutable. x.at[i].set(v) returns a new array, which XLA turns into an in-place update when it can prove that is safe.

PyTorch is comfortable with state. An nn.Module owns its parameters, optimizer.step() mutates them in place, and one global random generator is seeded at startup. This is familiar and often more concise. The cost is that knowing what a function does requires knowing what it touches.

Silicon: systolic arrays and streaming multiprocessors

Google built the TPU around one operation: dense matrix multiplication. The heart of a TPU core is the MXU, a systolic array of multiply-accumulate cells (128 × 128 on most generations, 256 × 256 on Trillium). Inputs flow in from one edge, partial sums flow down, weights stay put. No instruction fetch, no cache lookups, no thread scheduling: data marches through arithmetic in lockstep.

An NVIDIA GPU is a general-purpose parallel machine. Work is split into thousands of threads grouped in warps of 32 and scheduled across dozens of streaming multiprocessors, each with tensor cores for matmul and a hierarchy of caches and shared memory. Irregular workloads, dynamic shapes and hand-written kernels all fit, because the hardware finds parallelism at run time.

This is why the pairings are not accidental. A TPU has no hardware caches or out-of-order execution to paper over a bad schedule. The compiler must know every shape and plan every memory transfer ahead of time, which is exactly what XLA gets from a traced, static-shape program. A GPU tolerates eager, op-by-op execution because its schedulers and caches absorb the irregularity.

Scaling out: sharding by annotation

One chip is never enough. JAX's answer extends the compiler idea: describe a mesh of devices, say how each array is split across it with a PartitionSpec, and let XLA's SPMD partitioner insert the collectives (all-reduce, all-gather, reduce-scatter) that keep the math correct. The program you wrote is unchanged; the sharding is an annotation on the data.

PyTorch's stack grew the other way, from explicit communication upward. DistributedDataParallel replicates the model and all-reduces gradients with NCCL. FullyShardedDataParallel shards parameters and gathers them on demand. DTensor is the newer annotation-based layer that most resembles JAX's approach.

Which should you use?

Both are excellent. The question is which set of defaults matches your work.

Reach for JAX when

  • You are training or serving on TPUs, or scaling one program across hundreds of chips where compiler-managed sharding pays off.
  • Your model is a static-shape, matmul-heavy program and you want whole-program fusion without tuning.
  • You need higher-order derivatives, per-example gradients or other function transformations as first-class tools.

Reach for PyTorch when

  • You iterate quickly on GPUs with dynamic shapes, data-dependent control flow or lots of custom kernels.
  • You lean on the ecosystem: pretrained checkpoints, serving stacks and tutorials overwhelmingly target PyTorch first.
  • Your team thinks in objects and in-place updates and would rather opt into compilation than build around it.
